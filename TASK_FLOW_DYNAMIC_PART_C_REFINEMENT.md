# Phase 2c.1 — Refinement: Workflow-Author-Controlled Fields, Statuses, and Permissions

> **Status:** Proposed (not yet implemented). Phase 2c (workflow authoring + unified onboarding + snapshot-pin) has shipped. This refinement builds on top of 2c to fix a duplicate-question UX flaw and unbundle `flowType`.

## Why this exists

After 2c shipped, we hit a duplicate-question UX flaw in the workflow wizard: the 4-card picker (Start blank / Simple Project / Collaborative Project / Sales Pipeline) and the conversational skeleton's "What shape is this work?" step are the same choice in different clothes — the 3 templates correspond 1:1 to the 3 flow types. Anyone with a bit of common sense looking at the wizard catches that we're asking the same thing twice.

Deeper than the UX bug: `flowType` was doing too much. It controlled:

1. Which form fields appear on the new-project form
2. Which sidebar rows ProjectDetail renders
3. Which statuses are valid in the status picker
4. Who can update the project status
5. The WorkflowBadge color tone

Bundling all five behind a 3-way categorical choice (`basic` / `collaborative` / `individual`) is rigid — every tenant gets one of three takes whether or not it matches their work.

The fix: move the user-facing concerns (form fields, statuses, status permissions) off `flowType` and onto **explicit per-workflow config**, asked once in the wizard. `flowType` shrinks to "badge color tone" and stops being asked at all. The duplicate question disappears because we're no longer asking "what shape?" — we're asking concrete questions like "what info do you collect?" and "what statuses do projects move through?"

## Decisions captured up-front

- **Configurable form fields**: Workflow author picks which fields appear on the new-project form (description, deadline, submission date, presentation date), with `enabled` + `required` toggles and an optional custom label.
- **Configurable statuses**: Author picks from preset chips (the existing 8 `ProjectStatus` values) **or** creates custom statuses with a constrained color palette + a "counts as terminal" flag.
- **Configurable status permissions**: Author selects from a checklist of well-known actor types (owner, lead, project members, validator/coordinator/specialist team leads & members, admins) — filtered by the org structure so unconfigured roles don't appear.
- **No flow-type question anywhere**: It's never asked in the wizard. Stays on the doc as an optional cosmetic attribute (badge color).
- **Backward compatible**: Every new field is optional. Existing workflows render identically via legacy fallbacks.
- **No project migration**: `Project.status: string` is a strict widening of `Project.status: ProjectStatus`.

## Schema additions

### `/workflows/{id}` — new optional fields

```ts
export interface ProjectFieldsConfig {
  // Title and Owner are always on; not configurable here.
  description?: { enabled: boolean; required: boolean; placeholder?: string }
  deadline?: { enabled: boolean; required: boolean; label?: string }
  submissionDate?: { enabled: boolean; required: boolean; label?: string }
  presentationDate?: { enabled: boolean; required: boolean; label?: string }
  // Future expansion: customFields?: Array<{ id; label; type; required; options? }>
}

export type WorkflowStatusColor =
  | 'gray' | 'blue' | 'green' | 'mint' | 'amber' | 'red' | 'purple' | 'cyan'

export interface WorkflowStatusOption {
  id: string                  // stable id; what `project.status` stores
  label: string               // human label on the pill
  color: WorkflowStatusColor  // constrained to our palette
  isTerminal: boolean         // counts as "closed" for funnel/filter queries
}

export interface Workflow {
  // ... existing 2c fields unchanged

  projectFields?: ProjectFieldsConfig
  statusOptions?: WorkflowStatusOption[]
  // ActorRef list checked against the viewer when deciding whether the status
  // pill is clickable. Replaces usePermissions' flowType switch when present.
  canUpdateStatusActors?: ActorRef[]
}
```

### `projects/{projectId}.status` widening

Changes from `ProjectStatus` enum to `string`. Legacy projects carry the enum values, which become the default `statusOptions` ids on each seeded workflow — so existing data renders unchanged.

`ProjectStatus` stays exported as a documentation alias listing the 8 preset chip ids, used by seed defaults + the "preset chips" sub-picker in the wizard. Custom statuses are arbitrary string ids generated by the editor.

## Wizard redesign

Step indicator stays at 4 (different content, same count). The 4-card picker stays at step 1 but **no longer triggers a flow-type question** for the blank path — flow type is dead.

| Step | Title | What it collects |
| --- | --- | --- |
| 1 | Pick a starting point | Same 4 cards. Templates → straight to editor. Blank → goes to Step 2. |
| 2 | Name your workflow | name (required), description (optional). Same as today's Step 1. |
| 3 | What info do you collect? | `projectFields` checklist — Title/Owner shown as locked-on. Description / Deadline / Submission date / Presentation date each get an `enabled` toggle + `required` toggle + optional custom label. |
| 4 | Statuses + who can change them | `statusOptions` (preset chips + "Add custom" with name + color picker + terminal toggle) AND `canUpdateStatusActors` (checklist filtered by org config). |
| Editor | Side editor | Stages + actions. The Settings drawer also surfaces `projectFields`, `statusOptions`, `canUpdateStatusActors` so existing workflows can be edited. |

The "What shape?" step (`Step2FlowType.tsx`) is **deleted**.

### Status options sub-picker (Step 4 — left half)

Two-column layout:

- **Preset chips** (`STATUS_OPTIONS` list — each renders as a clickable chip with color preview). Toggle adds/removes from the workflow's `statusOptions`.
- **Custom statuses** — a `+ Add status` button reveals a small form: name (text, required), color (chip-row of the 8 allowed `WorkflowStatusColor` values), "counts as terminal" toggle. New custom status gets a generated id (`custom-${slug}`).

Each option in the workflow's `statusOptions` list can be reordered and removed; built-in chip-derived options keep their canonical id (`in_progress`, `completed`, etc.) so legacy projects on this workflow continue to resolve.

### Status permissions sub-picker (Step 4 — right half)

Checklist of actor types that gates the status pill on ProjectDetail. Filtered by the org config so we never surface a role that doesn't exist:

- ☐ The project's Owner
- ☐ The project's Lead *(disabled when the workflow has no `assign_lead` action anywhere)*
- ☐ Anyone on a team attached to the project
- ☐ Coordinator Team Lead *(only if `orgStructure.teamRoles.hasCoordinator`)*
- ☐ Coordinator Team members *(only if hasCoordinator)*
- ☐ Validator Team Lead *(only if hasValidator)*
- ☐ Validator Team members *(only if hasValidator)*
- ☐ Specialist Team Lead *(only if hasSpecialist)*
- ☐ Specialist Team members *(only if hasSpecialist)*
- ☐ Any global admin
- (Super-admin always allowed — shown as a locked-on row to make the baseline explicit)

Each checkbox writes one `ActorRef` into `workflow.canUpdateStatusActors`.

### isProjectClosed — generalize via workflow lookup

[src/lib/projectStatus.ts](src/lib/projectStatus.ts):

```ts
// New signature:
export function isProjectClosed(
  project: { status?: string; pinnedWorkflow?: Workflow },
): boolean {
  const status = project.status ?? 'in_progress'
  const opt = project.pinnedWorkflow?.statusOptions?.find((o) => o.id === status)
  if (opt) return opt.isTerminal
  // Legacy fallback — preserves behavior for projects pre-2c.1
  return ['completed', 'lost', 'not_submitted', 'archived'].includes(status)
}
```

All call sites currently pass `project.status`; they'll switch to passing the project itself.

## `flowType` after 2c.1

`flowType` stays on `Workflow` for back-compat but **never asked in the wizard**. It now only drives:

1. WorkflowBadge default color tone *(can be replaced by a workflow-level `color` setting later)*
2. Seed-file `projectFields` defaults *(internal, not user-facing)*
3. Legacy fallback paths in components that haven't yet had a chance to read the new fields

In the side editor's Settings drawer the flow-type dropdown can stay as an advanced/cosmetic control labeled "Card color" rather than "Flow type" — clearer about what it actually does post-2c.1.

---

## Backward compatibility

Every new field is **optional**. Workflows authored before 2c.1 (the three system seeds + any tenant-created ones) keep working because every reader has a `?? legacy` fallback. Seed files get updated to write the new fields with defaults that match today's behavior — so a fresh seed of `collab-default` ships with submission + presentation dates enabled, and an existing seed re-run lands the same shape.

Project documents need no migration: `Project.status: string` is a strict widening of `Project.status: ProjectStatus`. Existing string values stay valid.

## Risks & mitigations

- **Project.status widening.** Going from `ProjectStatus` enum to `string` removes type-narrowing across the codebase. Mitigation: every reader that branched on specific enum values either looks up `workflow.statusOptions` (the new mechanism) or falls back to the legacy `STATUS_DISPLAY` map keyed by the preset string ids. No runtime regression for projects whose status is one of the 8 preset values.
- **Custom status filter dropdowns.** The /projects status filter dropdown currently lists `STATUS_OPTIONS`. With custom statuses, that list should expand to include statuses defined across active workflows. Mitigation: derive the filter dropdown's options from `union(activeWorkflows.statusOptions)` instead of the hardcoded list. Existing legacy values stay because the seeded workflows declare them.
- **`flowType` dead code drift.** Components still branching on `flowType` for cosmetic things (badge color) can drift over time. Mitigation: leave a clearly-commented `// Cosmetic only — drives badge color. See workflow.projectFields / .statusOptions / .canUpdateStatusActors for behavioral splits` header on the remaining sites.
- **Wizard step count perception.** Adding a status step makes the wizard longer. Mitigation: Step 3 (Info) and Step 4 (Statuses+Permissions) both have sensible defaults pre-filled so a tenant who doesn't care can hammer "Continue" twice and get reasonable behavior — the wizard isn't punishing the user for not customizing.

6. **Copy review pass** — read every label aloud, fix anything that doesn't land.

Total scope: roughly 2–3 days on top of what's shipped.

## What this delivers

- The duplicate-question UX flaw in the workflow wizard is gone.
- Workflow authors control exactly what fields, statuses, and status permissions their projects use — instead of inheriting one of three opinionated `flowType` packages.
- `flowType` shrinks to a cosmetic concern that nobody needs to think about.
- The platform's "tenants shape their own workflows without code" promise extends from stages + actions all the way to project-level UI shape.

Phase 3's intelligence layer can lean on this richer per-workflow config to make better suggestions — e.g., a tenant whose `statusOptions` include "On Tour" gets event-vertical templates surfaced ahead of generic ones.
